# 串口通信契约（Python 层实现依据）

> 版本 v1 · 2026-11-06
> 本文是 **M2（串口打通）的实现契约**。FPGA 侧 M1 已完成，本文定义
> Python/上位机如何与板卡对话。
>
> **重要**：M1 阶段 FPGA **尚未实现 UART**。本文的帧格式是为 M2 预先约定的
> 设计目标，Python 层可以照此实现，但需要等 FPGA 侧 `uart_rx`/`frame_parser`
> 落地后才能端到端联调。

## 2. 帧结构

```
+--------+--------+--------+--------+----------+--------+
| 0xAA   | 0x55   | TYPE   | LEN    | PAYLOAD  | CRC8   |
+--------+--------+--------+--------+----------+--------+
  帧头1    帧头2    类型     载荷长   LEN 字节   校验
       └────── CRC 覆盖 TYPE, LEN, PAYLOAD ──────┘
```

| 字段 | 字节数 | 说明 |
|---|---|---|
| 帧头 | 2 | 固定 `AA 55`，用于重同步 |
| TYPE | 1 | bit7 = 方向（0=PC→FPGA，1=FPGA→PC）；bit6..0 = 消息号 |
| LEN | 1 | 载荷字节数，0–16 |
| PAYLOAD | LEN | 见各消息定义 |
| CRC8 | 1 | CRC-8/ATM，多项式 **0x07**，初值 **0x00** |

### 2.1 编解码要点

- **最长帧** = 4 + 16 + 1 = 21 字节，115200 下约 1.8 ms
- **多字节数值一律小端**（低位字节在前）
- **CRC 计算范围**：从 TYPE 开始，到 PAYLOAD 结束（不含帧头、不含 CRC 本身）
- **失败处理**：CRC 错或 LEN 越界 → **静默丢弃**，回到搜索帧头状态
  - 不回 NACK。错误帧引来错误帧会造成风暴
- **重同步**：因为 LEN 已知，载荷里偶然出现 `AA 55` 不会误判，CRC 会拦住

### 2.2 CRC-8/ATM 参考实现

```python
def crc8(data: bytes) -> int:
    """CRC-8/ATM: poly 0x07, init 0x00, no reflection, no final xor.

    Standard test vector: crc8(b"123456789") == 0xF4
    """
    crc = 0x00
    for byte in data:
        crc ^= byte
        for _ in range(8):
            if crc & 0x80:
                crc = ((crc << 1) ^ 0x07) & 0xFF
            else:
                crc = (crc << 1) & 0xFF
    return crc

# 自检：assert crc8(b"123456789") == 0xF4
```

> **这个函数必须先自检通过再往上搭。** `0xF4` 是 CRC-8/ATM 的标准锚点，
> 对不上说明多项式或位序写错了。

## 3. 消息定义

### 3.1 PC → FPGA（TYPE bit7 = 0）

#### `0x01` TIME_SYNC —— 校时

| 偏移 | 字段 | 取值 | 说明 |
|---|---|---|---|
| 0 | `hour` | 0–23 | 24 小时制 |
| 1 | `min` | 0–59 | |
| 2 | `sec` | 0–59 | |
| 3 | `day` | 1–7 | **星期几**（时间页 DK1 显示） |

LEN = 4。示例：设为 星期五 12:34:56

```
AA 55 01 04 0C 22 38 05 91
         │  │  │  │  └─ CRC8 = 0x91
         │  │  │  └──── day   = 5  (星期五)
         │  │  └─────── sec   = 0x38 = 56
         │  └────────── min   = 0x22 = 34
         └───────────── hour  = 0x0C = 12
```

> 这一帧的 CRC 是用 §2.2 的参考实现算出来的，可直接作为首个联调用例。
> 发送后板卡应显示 `5 12.34.56`。

#### `0x02` STATE_SET —— 状态置位

| 偏移 | 字段 | 取值 | 说明 |
|---|---|---|---|
| 0 | `state` | 0=FREE, 1=RUNNING, 2=WAITING | 驱动状态机与指示灯 |
| 1 | `session` | 0–15 | 会话号（当前不显示，预留） |
| 2 | `pending` | 0–255 | 待处理提问数（预留） |

LEN = 3。

> **在 M2 阶段，这个帧是状态机的唯一权威。** FPGA 的 `DEBUG_MODE` 参数要置 0，
> 否则中键会与 PC 抢控制权。

#### `0x03` QUESTION_OPEN —— 提问开始

| 偏移 | 字段 | 取值 | 说明 |
|---|---|---|---|
| 0 | `req_id` | 0–255 | 请求编号，回答时带回 |
| 1 | `n_options` | **1–9** | 本轮选项个数。**超过 9 个时上位机直接拒绝下发**（见下文） |
| 2 | `q_index` | 1–16 | 当前显示第几个问题 |

LEN = 3。收到后 FPGA 切到提问页显示 `ASH i-k`（`i`=问题序号，`k`=当前高亮选项）。

> **选项上限 9（索引 0–8）**：提问页第 6 位只能显示一个数字，超过 9 个选项
> 就没法表示。**Python 层负责在超过 9 个选项时不上报，板卡显示 `---`**，
> 此时用户应当回到键鼠去回答。这是刻意的分工——FPGA 只管一个数字，
> 复杂判断留给上位机。FPGA 侧的 `option_sel` 参数 `MAX_INDEX` 也固定为 8。

#### `0x04` QUESTION_CLOSE —— 提问结束

| 偏移 | 字段 | 取值 | 说明 |
|---|---|---|---|
| 0 | `req_id` | 0–255 | 对应 QUESTION_OPEN |

LEN = 1。

### 3.2 FPGA → PC（TYPE bit7 = 1）

#### `0x81` KEY_EVT —— 按键事件

| 偏移 | 字段 | 取值 | 说明 |
|---|---|---|---|
| 0 | `key_id` | 0=中(R15), 1=左(V1), 2=右(R11), **3=下(R17), 4=上(U4)** | 与 RTL 的 `key[4:0]` 一致 |
| 1 | `event` | 0=单击, 1=长按 | 长按阈值 800 ms |
| 2 | `state` | 0/1/2 | 按下瞬间的状态机快照 |

LEN = 3。

**语义由上位机解释**，FPGA 只报原始事件：

- **上(U4) / 下(R17)** = 切换高亮选项（**FPGA 本地已实现**，见 `option_sel.v`）
- 中(R15) = 确认当前选项
- 左(V1) / 右(R11) = 切换显示页
- 长按 = 预留

> **重要**：上/下键的选项增减是 **FPGA 本地逻辑**，不经过串口。
> 上位机只需要知道"用户最终确认了哪个选项"（由 `ANSWER` 帧上报），
> 不需要逐次转发上下键。这样即使串口暂时断开，选项切换依然可用。

> **注意：本设计不提供"拒绝"动作。** 拒绝通过"选中另一个选项"来表达。
> 因此 FPGA 上报的是**按键事件 + 选项索引**，不是"同意/拒绝"决策。

#### `0x82` ANSWER —— 回答结果

| 偏移 | 字段 | 取值 | 说明 |
|---|---|---|---|
| 0 | `req_id` | 0–255 | 对应 QUESTION_OPEN |
| 1 | `q_index` | 1–16 | 回答的是第几个问题 |
| 2 | `option` | **0–8** | 选中的选项索引，与提问页显示的数字一致 |
| 3 | `ms_hi` | 0–255 | 从收到请求到按键的毫秒数高位（可选） |

LEN = 4。

#### `0x83` STATUS_RPT —— 心跳/状态上报

| 偏移 | 字段 | 取值 | 说明 |
|---|---|---|---|
| 0 | `state` | 0/1/2 | 当前状态 |
| 1 | `session` | 0–15 | 当前会话号 |
| 2 | `pending` | 0–255 | 未处理提问数 |
| 3 | `flags` | bit0=按键中, bit1=时间有效, bit2=串口错 | |
| 4–5 | `uptime_s` | 0–65535（小端） | 上电秒计数，用于识别重启 |

LEN = 6。

**上报时机**：状态变化立即发 + **每 1 秒心跳一次**。

> 只发变化不够——断开重连后 PC 不知道板卡当前状态。心跳保证最终一致。

#### `0x00` ACK / `0x7F` NACK

- ACK：LEN=1，载荷是被确认的 TYPE
- NACK：LEN=1，载荷是被拒绝的 TYPE
- 收到 CRC 错/长度越界的帧**不回 NACK**（静默丢弃）
- 收到合法帧但语义不支持才回 NACK

## 4. Python 层建议结构

```
ego_bridge/
├── protocol.py      # 帧编解码 + CRC8（先自检 0xF4）
├── transport.py     # 串口打开/关闭/读写，端口自动发现
├── link.py          # 帧同步状态机（搜 AA55 → 读 TYPE/LEN → 收载荷 → 校验）
├── messages.py      # 各消息的 dataclass 与 pack/unpack
└── cli.py           # 手动调试入口
```

### 4.1 帧同步状态机（关键）

串口是**字节流**，必须自己找帧边界。推荐实现：

```
状态 IDLE   : 逐字节读，遇到 0xAA → WAIT_55
状态 WAIT_55: 读到 0x55 → READ_HDR；否则若又是 0xAA 停在 WAIT_55，否则回 IDLE
状态 READ_HDR: 收 TYPE + LEN（LEN > 16 视为非法，回 IDLE）
状态 READ_BODY: 收 LEN 字节载荷 + 1 字节 CRC
               CRC 通过 → 交付消息，回 IDLE
               CRC 失败 → 丢弃，回 IDLE（注意：载荷里可能有 AA 55，不要回退重扫）
```

> **CRC 失败后不要从载荷中间重新找帧头。** 那样会在错误帧里反复误同步。
> 直接丢弃整帧、等下一个真实帧头，更稳。

### 4.2 超时与重试

| 场景 | 建议 |
|---|---|
| 等 ACK | 50 ms 超时，重发 3 次 |
| 心跳丢失 | 连续 3 秒没收到 STATUS_RPT → 标记链路断开 |
| 串口打开失败 | 列出可用端口让用户选，不要硬编码 COM7 |
| 串口读线程 | 独立线程，队列交付上层，避免阻塞 UI |

**先不接 DSH**，用串口调试助手或 Python 脚本即可验证：

| # | 操作 | 期望现象 |
|---|---|---|
| 1 | 发 `AA 55 01 04 0C 22 38 05 91` | 板卡显示 `5 12.34.56` |
| 2 | 发 STATE_SET state=1 | K6 开始 1 Hz 慢闪 |
| 3 | 发 STATE_SET state=2 | K6 变常亮 |
| 4 | 发 STATE_SET state=0 | K6 灭 |
| 5 | 发 QUESTION_OPEN (req=5, n_opt=3, index=1) | 显示 `ASH 1-0`（选项 0） |
| 6 | 按上(U4) 两次 | 显示 `ASH 1-2`，选项数字递增 |
| 7 | 按下(R17) 一次 | 显示 `ASH 1-1`，选项数字递减 |
| 8 | 按中键 | 收到 `ANSWER` 帧，`option=1` |
| 9 | 故意改坏 1 个 CRC 字节 | 板卡无变化，不死机 |
| 10 | 不操作 5 秒 | 每秒收到一帧 `STATUS_RPT` |
| 11 | 拔掉串口再插回 | 板卡不锁死，重新握手后状态恢复 |

> **第 1 条是首选联调用例**：CRC 已用 §2.2 的参考实现实算验证过。
> 如果这一帧能让板卡显示正确时间，说明波特率、引脚方向、帧格式、CRC 全部正确。
>
> **第 6–8 条是选项切换的端到端验证**：选项数字是 FPGA 本地逻辑，
> 上位机只需确认最终 `ANSWER` 里的 `option` 与屏幕上看到的一致。

## 6. 与 DSH 的衔接（M3 才需要）

Python 层最终会作为 DSH host 插件的**串口后端**，或独立进程。

需要挂钩的三个 DSH 事件（详见 `DESIGN.md` §4）：

| DSH 事件 | 转成的帧 |
|---|---|
| `agent/status` 变化 | `STATE_SET` |
| `user-questions/request` 进入 | `QUESTION_OPEN` |
| `approval/request` 进入 | `QUESTION_OPEN`（kind 不同） |
| FPGA 回 `ANSWER` | 构造 `AskUserQuestionAnswer` 返回给 waterfall |

**两个 seam 都要挂**（`userQuestions` 和 `approval`），否则会漏掉一半交互。
