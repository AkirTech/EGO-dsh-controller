# 串口通信契约（Python 层实现依据）

> 版本 **v2.1** · 2026-11-07
> 本文是 **M2（串口打通）/ M3（DSH 桥接）的实现契约**。FPGA 侧 M1 已完成，
> 本文定义 FPGA ↔ Python ↔ DSH 三层如何对话。

---

## 0. v2 相对 v1 的改动

| # | 改动 | 理由 |
|---|---|---|
| 1 | `0x82 ANSWER` 载荷 `req_id, q_index, option, ms_lo, ms_hi`，**LEN = 5** | v1 只给了 `ms_hi` 没有 `ms_lo`，字段残缺无法实现。改为 16 位小端毫秒 |
| 2 | **提问态（WAITING 且有未关闭请求）按中键只发 `ANSWER`，不再同时发 `KEY_EVT`** | v1 会连发两帧，上位机必须写去重逻辑。约定由 FPGA 侧分流 |
| 3 | **取消 ACK 阻塞等待**。ACK 帧仍在协议里（保留 `0x00`），但上位机**不阻塞等 ACK**，靠 1 Hz `STATUS_RPT` 心跳 + 变化重发兜底 | v1 §4.2 的「等 ACK 50 ms 超时重发 3 次」与 FPGA 侧是否实现 ACK 未对齐，且会引入重传风暴 |
| 4 | `day` 明确为 **周一 = 1 … 周日 = 7** | v1 只写 1–7，两端理解可能不同 |
| 5 | 新增 `0x05 TIME_SET_ACK` 之外的**连接握手约定**（见 §3.4） | M3 要求「每次 Python 连上就同步系统时间」 |
| 6 | 新增 §7 Python 层与 DSH 插件之间的 JSON 行协议 | 本轮桥接架构是「Python 守串口 + 插件 spawn 子进程」 |

> **关于本轮范围**：M2/M3 实现 `TIME_SYNC` / `STATE_SET` / `STATUS_RPT` / `KEY_EVT`
> 全链路；`QUESTION_OPEN` / `QUESTION_CLOSE` / `ANSWER` 的**帧格式与 FPGA 解析已实现**，
> 但 DSH 插件本轮**不挂** `user-questions/request` 和 `approval/request`，
> 因此提问通路只在串口层面可用（可用 `cli.py` 手动触发验证）。

| 项目 | 值 | 依据 |
|---|---|---|
| 桥接芯片 | **手册未给出型号**。板子只暴露一个 USB 设备 `VID_03FD&PID_0008`（Xilinx USB Cable） | **实机枚举**（见下方 §1.1） |

### 1.1 实机枚举结果（2026-11-11，板子已插）

用 `Get-CimInstance Win32_PnPEntity` 枚举，**整块板子在 USB 上只有一个节点**：

```
USB\VID_03FD&PID_0008   Xilinx USB Cable
  Service            : WinDriver6           (Xilinx 专有驱动)
  Class              : Programming cables
  CompatibleIds      : USB\Class_FF         (厂商自定义类)
  BusReportedDeviceDesc: "XILINX"
```

同时确认：

| 检查项 | 结果 |
|---|---|
| `VID_10C4`（CP210x） | **不存在** |
| 任何 `COMx` 归属本板 | **没有**（系统里 8 个 COM 全是 `BTHENUM` 蓝牙虚拟串口） |
| 有错误码的设备 | 无（即不是"驱动没装好"，是根本没枚举出来） |
| 同一 USB 容器内其它节点 | 无（只有这一个） |

**结论：目前拿不到板子的串口。** `VID_03FD&PID_0008` 是 Xilinx/Digilent
的 FTDI 双通道器件被 Xilinx 固件重新枚举后的形态，整个芯片被 WinDriver
独占成一个 `Class_FF` 接口；第二个通道（UART）没有作为独立 USB 接口暴露
给 Windows。

> **历史更正**：本文 v1/v2 写的"CP2102"**是错的**。官方手册从头到尾没有
> 出现这个型号，那是一次未经核实的臆断。真实情况见上表。

### 1.2 对 Python 层的影响

`transport.py` 的端口发现逻辑原本按 **CP210x 的 VID=0x10C4 / PID=0xEA60**
匹配，在这块板上**永远不会命中**。在拿到可用串口之前，`--port COMx`
只能手工指定，自动发现必然失败。

可选的解决方向见 [`DESIGN.md`](DESIGN.md) §6.2。在解决之前，
**Python 层实际只能跑 `--sim` 模拟器**，无法与真板通信。

## 2. 帧结构

```
+--------+--------+--------+--------+----------+--------+
| 0xAA   | 0x55   | TYPE   | LEN    | PAYLOAD  | CRC8   |
+--------+--------+--------+--------+----------+--------+
  帧头1    帧头2    类型     载荷长   LEN 字节   校验
       └────── CRC 覆盖 TYPE, LEN, PAYLOAD ──────┘
```

| 字段 | 字节数 | 说明 |
|---|---|---|
| 帧头 | 2 | 固定 `AA 55`，用于重同步 |
| TYPE | 1 | bit7 = 方向（0=PC→FPGA，1=FPGA→PC）；bit6..0 = 消息号 |
| LEN | 1 | 载荷字节数，**0–8**（v2 收紧，见下） |
| PAYLOAD | LEN | 见各消息定义 |
| CRC8 | 1 | CRC-8/ATM，多项式 **0x07**，初值 **0x00** |

> **LEN 上限从 16 收紧到 8。** 已定义的消息最长 6 字节（`STATUS_RPT`）。
> FPGA 侧接收缓冲只要 8 字节，`frame_parser` 的越界判断也简单。
> 超过 8 的 LEN 一律视为非法帧丢弃。

### 2.1 编解码要点

- **最长帧** = 4 + 8 + 1 = 13 字节，115200 下约 1.13 ms
- **多字节数值一律小端**（低位字节在前）
- **CRC 计算范围**：从 TYPE 开始，到 PAYLOAD 结束（不含帧头、不含 CRC 本身）
- **失败处理**：CRC 错或 LEN 越界 → **静默丢弃**，回到搜索帧头状态
  - 不回 NACK。错误帧引来错误帧会造成风暴
- **重同步**：因为 LEN 已知，载荷里偶然出现 `AA 55` 不会误判，CRC 会拦住

### 2.2 CRC-8/ATM 参考实现

```python
def crc8(data: bytes) -> int:
    """CRC-8/ATM: poly 0x07, init 0x00, no reflection, no final xor.

    Standard test vector: crc8(b"123456789") == 0xF4
    """
    crc = 0x00
    for byte in data:
        crc ^= byte
        for _ in range(8):
            if crc & 0x80:
                crc = ((crc << 1) ^ 0x07) & 0xFF
            else:
                crc = (crc << 1) & 0xFF
    return crc

# 自检：assert crc8(b"123456789") == 0xF4
```

对应 Verilog 的位并行等价形式（每拍处理 1 位，`frame_parser` 里就是这么写的）：

```verilog
crc <= crc[7] ? ((crc << 1) ^ 8'h07) : (crc << 1);
crc <= crc ^ {7'b0, bit_in};   // 先异或再移位，与上面 Python 的顺序一致
```

> **这个函数必须先自检通过再往上搭。** `0xF4` 是 CRC-8/ATM 的标准锚点，
> 对不上说明多项式或位序写错了。

## 3. 消息定义

TYPE 的 bit7 表示方向，所以同一类消息在两侧看到的值不同：
`0x81` 在线上是 `0x81`（FPGA→PC），PC 发同一消息号则为 `0x01`。

### 3.1 PC → FPGA（TYPE bit7 = 0）

#### `0x01` TIME_SYNC —— 校时

| 偏移 | 字段 | 取值 | 说明 |
|---|---|---|---|
| 0 | `hour` | 0–23 | 24 小时制 |
| 1 | `min` | 0–59 | |
| 2 | `sec` | 0–59 | |
| 3 | `day` | **1–7，周一=1 … 周日=7** | 时间页 DK1 显示 |

LEN = 4。示例：设为 星期五 12:34:56

```
AA 55 01 04 0C 22 38 05 91
         │  │  │  │  └─ CRC8 = 0x91
         │  │  │  └──── day   = 5  (星期五)
         │  │  └─────── sec   = 0x38 = 56
         │  └────────── min   = 0x22 = 34
         └───────────── hour  = 0x0C = 12
```

> 这一帧的 CRC 是用 §2.2 的参考实现实算出来的，可直接作为首个联调用例。
> 发送后板卡应显示 `5 12.34.56`。
>
> **语义是"瞬间装载 + 从此本地走时"**，不是周期性对齐。Python 层在
> **每次串口打开成功后立即发一次**，之后靠 FPGA 自己的 1 Hz 计数走时。
> 若上层需要长期对齐，由 Python 每小时补发一次（`--resync-hourly`）。

#### `0x02` STATE_SET —— 状态置位

| 偏移 | 字段 | 取值 | 说明 |
|---|---|---|---|
| 0 | `state` | 0=FREE, 1=RUNNING, 2=WAITING | 驱动状态机与指示灯 |
| 1 | `session` | 0–15 | 会话号（当前不显示，预留） |
| 2 | `pending` | 0–255 | 待处理提问数（预留） |

LEN = 3。

> **在 M2 阶段，这个帧是状态机的唯一权威。** `DEBUG_MODE` 参数置 0，
> 否则中键会与 PC 抢控制权。
>
> `state` 非法（>2）或 `session` 非法（>15）时 FPGA **回 `NACK(0x02)`**，
> 且**状态保持不变**。v1 这里曾写"忽略该帧、不发 NACK"，与同节 NACK 条目
> 及 §5 第 12 条矛盾；v2.1 统一为回 NACK，理由见 §3.3。

#### `0x03` QUESTION_OPEN —— 提问开始

| 偏移 | 字段 | 取值 | 说明 |
|---|---|---|---|
| 0 | `req_id` | 0–255 | 请求编号，回答时带回 |
| 1 | `n_options` | **1–9** | 本轮选项个数。**超过 9 个时上位机直接拒绝下发** |
| 2 | `q_index` | 1–16 | 当前显示第几个问题 |

LEN = 3。收到后 FPGA 切到提问页显示 `ASH i-k`（`i`=问题序号，`k`=当前高亮选项），
**同时把 `option_sel` 的活动上限设为 `n_options - 1`**。

> **选项上限 9（索引 0–8）**：提问页第 6 位只能显示一个数字。
> Python 层负责在超过 9 个选项时不上报，板卡不处理"10"。

#### `0x04` QUESTION_CLOSE —— 提问结束

| 偏移 | 字段 | 取值 | 说明 |
|---|---|---|---|
| 0 | `req_id` | 0–255 | 对应 QUESTION_OPEN |

LEN = 1。FPGA 收到后清提问态、选项归零。

#### `0x7F` NACK（FPGA→PC 方向也用 `0xFF`）

- LEN=1，载荷是被拒绝的 TYPE
- **只在收到合法 CRC/长度、但语义不支持时发**（例如 `STATE_SET` 的 `state=3`）
- CRC 错/长度越界的帧一律静默丢弃，不回 NACK

### 3.2 FPGA → PC（TYPE bit7 = 1）

#### `0x81` KEY_EVT —— 按键事件

| 偏移 | 字段 | 取值 | 说明 |
|---|---|---|---|
| 0 | `key_id` | 0=中(R15), 1=左(V1), 2=右(R11), **3=下(R17), 4=上(U4)** | 与 RTL 的 `key[4:0]` 一致 |
| 1 | `event` | 0=单击, 1=长按 | 长按阈值 800 ms |
| 2 | `state` | 0/1/2 | 按下瞬间的状态机快照 |

LEN = 3。

**v2 的关键分流规则（FPGA 侧实现）：**

| 条件 | 上报 |
|---|---|
| 存在未关闭的提问（`q_open=1`）**且**按的是中键（`key_id=0`）单击 | **只发 `ANSWER`**，不发 `KEY_EVT` |
| 其他任何按键事件 | 发 `KEY_EVT` |

> 理由：提问态按中键的语义是"确认当前选项"，上位机只关心最终答案。
> 发两帧会让上位机必须做 `(req_id, q_index)` 去重，而 FPGA 本来就知道
> 自己处在提问态 —— 由状态更多的一方分流，比让上位机猜更可靠。
>
> **上/下键的选项增减是 FPGA 本地逻辑**，不经过串口，也不上报 `KEY_EVT`。
> 这样即使串口暂时断开，选项切换依然可用。

#### `0x82` ANSWER —— 回答结果

| 偏移 | 字段 | 取值 | 说明 |
|---|---|---|---|
| 0 | `req_id` | 0–255 | 对应 QUESTION_OPEN |
| 1 | `q_index` | 1–16 | 回答的是第几个问题 |
| 2 | `option` | **0–8** | 选中的选项索引，与提问页显示的数字一致 |
| 3–4 | `elapsed_ms` | 0–65535（**小端**） | 从 `QUESTION_OPEN` 到确认的毫秒数，饱和不回绕 |

LEN = **5**。

```
AA 55 82 05 05 01 02 D2 04 1F
         │  │  │  │  │  └── 0x041F... 见下
         │  │  │  └──┴──── elapsed_ms = 0x04D2 = 1234 ms
         │  │  └──────── option = 2
         │  └─────────── q_index = 1
         └────────────── req_id = 5
```

> `elapsed_ms` 在 65.535 s 处**饱和**而不是回绕 —— 回绕会让 66 s 的等待
> 看起来像 1 s，而饱和只是失去精度。上限由 FPGA 内部 16 位计数保证。

#### `0x83` STATUS_RPT —— 心跳/状态上报

| 偏移 | 字段 | 取值 | 说明 |
|---|---|---|---|
| 0 | `state` | 0/1/2 | 当前状态 |
| 1 | `session` | 0–15 | 当前会话号 |
| 2 | `pending` | 0–255 | 未处理提问数 |
| 3 | `flags` | bit0=按键中, bit1=时间有效, bit2=串口错 | |
| 4–5 | `uptime_s` | 0–65535（小端） | 上电秒计数，用于识别重启 |

LEN = 6。

**上报时机**：状态变化立即发（下一拍就发，不等心跳）+ **每 1 秒心跳一次**。

> 只发变化不够——断开重连后 PC 不知道板卡当前状态。心跳保证最终一致。
>
> `flags` 的 **bit1「时间有效」**是 v2 新增的实际用途：上电后 `ce_1hz` 从未
> 收到过 `TIME_SYNC` 时该位为 0，Python 层据此判断「要不要补发时间」，
> 而不是盲目每秒重发。`uptime_s` 变化则说明板卡重启过，需要重新握手。

#### `0x00` ACK（两个方向都可能出现，但 **v2 不依赖**）

- LEN=1，载荷是被确认的 TYPE
- FPGA 本轮**不主动发 ACK**（只在收到合法帧后记录，不占用带宽）
- Python 层**不阻塞等 ACK**：发送即返回，靠心跳与 `STATUS_RPT` 的字段变化确认生效
- 保留这个 TYPE 是为了将来需要强确认时有编号可用

### 3.3 按键映射

| keyId | 物理键 | 单击 | 长按（>800 ms） |
|---|---|---|---|
| 0 | R15（中） | **确认当前选项** | 预留 |
| 1 | V1（左） | 切换显示页 | 预留 |
| 2 | R11（右） | 切换显示页 | 预留 |
| **3** | **R17（下）** | **选项 −1** | 预留 |
| **4** | **U4（上）** | **选项 +1** | 预留 |

> 上/下键只在提问态生效，且此时显示页被强制锁定在第 2 页（ASK 页）。

> **本设计不提供"拒绝"动作**（见 §9 已确认决策）。拒绝通过"选中另一个选项"表达。

### 3.4 错误处理的两个方向（为什么 CRC 错不 NACK、字段越界却 NACK）

这两条规则看着矛盾，其实是对两类完全不同的错误分别处理：

| 错误类型 | 例子 | 处理 | 原因 |
|---|---|---|---|
| **传输意外** | CRC 错、LEN > 8、帧头丢失 | **静默丢弃** | 线路噪声造成的。回 NACK 会引来更多帧、更多噪声，形成错误风暴；丢一帧等下一帧即可自愈 |
| **语义错误** | `state=3`、`session=20`、`n_options=0` | **回 NACK** | 对端程序写错了。静默丢弃会让对方以为发送成功，bug 永远发现不了 |

判断依据是**「重发同一帧会不会有不同结果」**：不会（噪声是随机的）就丢弃，
会（对端该改代码）就 NACK。

### 3.5 连接握手（v2 新增）

Python 层每次打开串口后按以下顺序做，**不等待 ACK**：

```
1. 打开端口 115200 8N1，清空输入缓冲
2. 发 TIME_SYNC（系统本地时间 + 周一=1 的星期）
3. 发 STATE_SET（当前 DSH 状态；未知则发 FREE）
4. 开始读流，等待 STATUS_RPT
   - 3 s 内收到任意一帧 → 判定链路 up
   - 3 s 无帧 → 判定链路 down，进入重连（指数退避 1/2/4/8 s 上限 8 s）
5. 链路 up 期间：
   - 每收到一次 uptime_s 回退 → 判定板卡重启 → 重做步骤 2、3
   - 每 <1 s> 收不到 STATUS_RPT 累计 3 次 → 判定链路 down
```

> **为什么不用 ACK 做握手**：FPGA 侧若漏掉一帧（USB 缓冲、复位窗口），
> 等 ACK 的上位机会重发 3 次然后报错；而心跳是**无条件周期广播**，
> 丢一帧下一帧就补上，天然自愈。这里用「最终一致」替代「请求-确认」。

### 3.6 交互时序（提问通路，本轮仅串口层可用）

```
PC                                    FPGA
   |  AA 55 03 03 05 03 01 64           |  QUESTION_OPEN: req=5, n_opt=3, index=1
   |────────────────────────────────────>|  状态 → WAITING（K6 常亮）
   |                                     |  显示页 → "ASH 1-0"
   |                                     |
   |                                     |  用户按上(U4) 两次，FPGA 本地选项 0→2
   |                                     |  用户按中(R15) 确认
   |  AA 55 82 05 05 01 02 D2 04 1F      |  ANSWER: req=5, idx=1, option=2, 1234 ms

   |────────────────────────────────────>|  状态 → RUNNING（K6 慢闪）

```

> 注意：提问态按中键**只有 `ANSWER` 一帧**，没有 `KEY_EVT`（见 §3.2 v2 分流规则）。

## 4. Python 层结构

```
├── protocol.py      # 帧编解码 + CRC8（先自检 0xF4）

├── bridge.py        # 状态聚合、心跳监测、重连、时间同步

```

### 4.1 帧同步状态机（关键）

串口是**字节流**，必须自己找帧边界：

```
状态 IDLE   : 逐字节读，遇到 0xAA → WAIT_55
状态 WAIT_55: 读到 0x55 → READ_HDR；否则若又是 0xAA 停在 WAIT_55，否则回 IDLE
状态 READ_HDR: 收 TYPE + LEN（LEN > 8 视为非法，回 IDLE）
状态 READ_BODY: 收 LEN 字节载荷 + 1 字节 CRC
                CRC 通过 → 交付消息，回 IDLE
                CRC 失败 → 丢弃，回 IDLE（注意：载荷里可能有 AA 55，不要回退重扫）
```

> **CRC 失败后不要从载荷中间重新找帧头。** 那样会在错误帧里反复误同步。
> 直接丢弃整帧、等下一个真实帧头，更稳。

### 4.2 超时与重试

| 场景 | 做法 |
|---|---|
| 发送 | **不阻塞等 ACK**；写失败立即抛给上层，由 bridge 触发重连 |
| 心跳丢失 | 连续 3 秒没有 `STATUS_RPT` → 标记链路断开，重连 |
| 板卡重启 | `uptime_s` 回退 → 重发 TIME_SYNC + STATE_SET |
| 串口打开失败 | 列出可用端口让用户选，不要硬编码 COM7 |
| 串口读线程 | 独立线程，队列交付上层，避免阻塞 UI |

## 6. Python 层与 DSH 插件的接口（v2 新增）

插件 **spawn** `python -m ego_bridge.service --port COMx`，双方走 **stdin/stdout 上的
JSON Lines**（每行一个 JSON 对象，UTF-8 无 BOM）。stderr 只用于日志，不参与协议。

### 6.1 插件 → Python（命令）

| `cmd` | 字段 | 说明 |
|---|---|---|
| `hello` | `version` | 请求 Python 上报版能力与链路状态 |
| `set_state` | `state` (0/1/2), `session` (0–15), `pending` (0–255) | 转成 `STATE_SET` |
| `sync_time` | `epoch_ms` (int) | 用给定时刻校时；缺省用 Python 本机时间 |
| `question_open` | `req_id`, `n_options`, `q_index` | 预留，本轮插件不调用 |
| `question_close` | `req_id` | 预留 |
| `ping` | — | 健康检查 |
| `shutdown` | — | 优雅退出 |

### 6.2 Python → 插件（事件）

| `evt` | 字段 | 说明 |
|---|---|---|
| `ready` | `version`, `port`, `sim` | 进程启动完成 |
| `link` | `up` (bool), `reason` | 链路状态变化 |
| `status` | `state`, `session`, `pending`, `flags`, `uptime_s` | 透传 `STATUS_RPT`（已去重，只在变化时发） |
| `key` | `key_id`, `event`, `state` | 透传 `KEY_EVT` |
| `answer` | `req_id`, `q_index`, `option`, `elapsed_ms` | 透传 `ANSWER` |
| `error` | `code`, `message` | 任何致命错误 |
| `pong` | — | 对 `ping` 的响应 |

> **Python 侧只做协议翻译和链路健康，不做 DSH 语义。**
> 「idle 对应 FREE」这类映射属于插件，不在这里 —— 否则换一个宿主（比如
> 一个纯 Qt 面板）就得改 Python。
